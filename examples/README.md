# Два примера на реальных товарах

Все исходные JSON подготовлены **только** из `feed.xml` заказчика — без переходов на сайт, поиска паспортов или добавления технических характеристик:

| Файл | XML offer id | URL из XML |
| --- | --- | --- |
| `input_mk110.json` | `54079` | https://www.souz-pribor.ru/product/mk110-8d-4r/ |
| `input_testo_830_t1.json` | `64423` | https://www.souz-pribor.ru/product/testo-830-t1/ |

Поля `name`, `manufacturer`, `description` получены из товарного обозначения, производителя и `typePrefix` соответствующей записи выгрузки. `specs` содержит исходные значения `param`, **только артикул и код товара**. Полноценными техническими характеристиками эти поля не являются.

`observed_v2_*.json` — **фактические ответы**, полученные при финальных ручных вызовах локального Codex CLI с промптом v2 и обновлённой предобработкой. Пользователь подтвердил успешные ответы API со статусом `needs_review` для обеих карточек.

В обоих результатах `missing_fields: ["technical_specs"]` и предупреждение о том, что в исходных данных есть только каталожные идентификаторы, а не технические характеристики. При этом SEO-заголовки, SEO-описания, запросы и коммерческие блоки заполнены. Это **черновики**, а не полностью готовые технические описания. Точные тексты LLM при повторных запусках могут отличаться.
`generated` означает лишь прохождение реализованных программных проверок, а `needs_review` — черновик, требующий участия контент-менеджера. Ни один из статусов не подтверждает SEO-эффективность или абсолютную фактическую точность.

**Внешние сайты и паспортные данные в этой демонстрации не использовались.**
