# Items Description — AI-помощник для подготовки товарных описаний

Локальный прототип на **Python 3.12+ / FastAPI**, который по JSON с известными сведениями о товаре создаёт **черновик** SEO-карточки для B2B-каталога. Использует LLM со структурированным ответом, проверяет формальные ограничения и сообщает о нехватке входных данных.

Проект выполнен по тестовому заданию «AI-помощник для подготовки товарных описаний». **Парсинг сайтов, XML-импорт и автоматическое обогащение характеристик не реализованы:** это отдельный возможный этап, не входящий в обязательный API генерации.

## Что реализовано

- `POST /generate`: принимает имя, производителя, словарь характеристик и описание товара.
- LLM генерирует `seo_title` (не более 70 символов), `seo_description` (целевой диапазон 800–1200 символов), 3–5 `search_queries`, `commercial_block`.
- `characteristics` переносятся **строго из входных данных**, без дополнения моделью.
- Предобработка исключает неизвестные значения; отделяет артикулы и каталожные коды от собственно технических характеристик.
- Если у товара только идентификаторы и краткое описание, сервис может вернуть **SEO-черновик с `needs_review`**, `missing_fields: ["technical_specs"]` и предупреждением. Если нет даже описания или технических сведений — `insufficient_data` без LLM.
- Программные проверки: длина полей, уникальность запросов, непустой коммерческий блок; эвристики для отсутствующих в источнике чисел, единиц измерения, IP-классов и некоторых коммерческих утверждений.
- При ошибках генерируемого текста — не более двух дополнительных LLM-вызовов; исходные факты при этом не изменяются.
- Фильтрация очевидных попыток внедрить инструкции в товарные поля. Это не абсолютная защита.
- `GET /healthz`, интерактивный Swagger UI, тесты, Ruff, Pyright.

## Быстрый запуск

### 1. Установка

Windows PowerShell:

```powershell
git clone https://github.com/ForerunnerDeath/items_description.git
cd items_description
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -e ".[dev]"
Copy-Item .env.example .env
```

Для macOS/Linux: `python3 -m venv .venv`, `source .venv/bin/activate`, `cp .env.example .env`.

### 2. Подключение LLM API (основной режим)

Укажите в локальном `.env`:

```dotenv
LLM_BACKEND=openai
LLM_MODEL=gpt-4o-mini
LLM_API_KEY=YOUR_API_KEY
LLM_BASE_URL=
LLM_MAX_TOKENS=2048
LLM_TIMEOUT_SECONDS=30
```

- `LLM_MODEL` — имя модели провайдера, поддерживающей **Structured Outputs / JSON Schema**.
- `LLM_API_KEY` — API-ключ. `.env` исключён из Git, ключ нельзя коммитить.
- `LLM_BASE_URL` — необязательный URL OpenAI-совместимого API. Для локального сервера с указанным URL API-ключ может быть пустым.
- Совместимость зависит от провайдера: используется `AsyncOpenAI.chat.completions.parse()` с Pydantic-моделью `LLMGeneratedContent`.
- **Важно:** клиент API и его обработка ошибок покрыты автоматическими тестами с подставными ответами; реальный запрос к платному API в рамках представленных испытаний **не выполнялся**.

### 3. Альтернативный локальный режим Codex CLI

Для ручной демонстрации без отдельного API-ключа можно использовать **установленный и авторизованный Codex CLI**:

```powershell
codex --version
codex login status
```

При необходимости выполните `codex login`. Затем измените `.env`:

```dotenv
LLM_BACKEND=codex_cli
LLM_CODEX_MODEL=
LLM_CODEX_TIMEOUT_SECONDS=180
```

Этот режим **фактически испытан на двух товарах из выгрузки** (см. `examples/`). Он запускает локальный процесс `codex exec`, работает через уже существующую авторизацию ChatGPT и **не является проверкой платного LLM API**. Не используйте его для публичного сервиса: он может расходовать лимиты аккаунта, а ограниченный sandbox не гарантирует отсутствие сетевых обращений.

### 4. Старт и запрос

```powershell
python -m uvicorn app.main:app --reload
```

Откройте http://127.0.0.1:8000/docs, выберите `POST /generate`, нажмите **Try it out** и вставьте содержимое одного из файлов:

- [examples/input_mk110.json](examples/input_mk110.json)
- [examples/input_testo_830_t1.json](examples/input_testo_830_t1.json)

Также можно отправить запрос из PowerShell:

```powershell
$json = Get-Content .\examples\input_mk110.json -Raw -Encoding UTF8
$body = [System.Text.Encoding]::UTF8.GetBytes($json)
Invoke-RestMethod -Method Post -Uri "http://127.0.0.1:8000/generate" -ContentType "application/json; charset=utf-8" -Body $body
```

Пример входного JSON:

```json
{
  "name": "МК110-224.8Д.4Р [М01]",
  "manufacturer": "ОВЕН",
  "specs": {
    "Артикул": "58953",
    "Код товара": "63483"
  },
  "description": "комбинированный модуль ввода/вывода дискретных сигналов"
}
```

**Данные без технических параметров:** после предобработки в результате ожидаются `status: "needs_review"`, `missing_fields: ["technical_specs"]` и поясняющий `warnings`. При этом SEO-черновик, если создан моделью, возвращается полностью. Точные формулировки LLM могут отличаться между запусками.

## Два реальных примера из feed.xml

Использованы **два товара из предоставленной заказчиком выгрузки**, без обращения к их страницам в интернете и без добавления характеристик:

| Модель | Что передано в модель |
| --- | --- |
| **МК110-224.8Д.4Р [М01]**, ОВЕН | Название, производитель, краткий тип изделия, артикул `58953`, код товара `63483`. |
| **testo 830-T1**, Testo | Название, производитель, краткий тип прибора с лазерным целеуказателем, артикул `0560 8311`, код товара `12387`. |

В `examples/` лежат два оригинальных входных JSON, два **фактически полученных ответа** с локального Codex CLI и [описание происхождения данных](examples/README.md).

Внимание: файлы `observed_v2_*.json` фиксируют **ручные результаты до улучшения проверки полноты данных**. Поэтому в них исторически стоит `status: "generated"`. В текущей версии проекта такие входные JSON намеренно приводят к `needs_review`: информация позволяет создать черновик, но **не позволяет утверждать, что описание технически полное**. Актуальный результат необходимо получать новым вызовом API; текст модели не детерминирован.

## Статусы, формат и ошибки

Ответ содержит `status`, `seo_title`, `seo_description`, `characteristics`, `search_queries`, `commercial_block`, `missing_fields`, `warnings`.

| Статус | Когда возвращается |
| --- | --- |
| `generated` | Формальные/эвристические проверки пройдены и нет предупреждений предобработки. Это **не** независимая проверка фактической точности. |
| `needs_review` | Черновик создан, но есть проблемы с полнотой данных или качеством текста; либо выявлены подозрительные инструкции во входе. |
| `insufficient_data` | Недостаточно содержательных данных для обращения к LLM. |

HTTP: `200` — обработанный результат; `422` — невалидный JSON/схема; `502` — ошибка LLM/непригодный структурированный ответ; `503` — не настроен основной LLM-бэкенд.

## Промпты и инженерные решения

**[app/prompts.py](app/prompts.py) — версия v2.**

Системный промпт фиксирует, что **единственным источником фактов о товаре является переданный JSON**. Модель не должна пользоваться знаниями о конкретных модификациях, добавлять характеристики, цены, совместимость, гарантию и другие неподтверждённые сведения. При коротком вводе разрешены нейтральные редакторские формулировки, но не бессмысленные повторы, выдумки и раскрытие внутренних ограничений в SEO-тексте.

Данные товара сериализуются отдельно в user prompt. Модель выдаёт только четыре текстовых SEO-поля, а `characteristics` собирает Python из нормализованных исходных параметров.

После получения ответа:
1. Проверяется Pydantic-схема.
2. Проверяются длина заголовка и описания, количество/уникальность запросов.
3. Эвристики помечают часть неподтверждённых чисел, размерностей и коммерческих заявлений.
4. При исправимых ошибках даётся не более двух повторных попыток с диагностикой; недостающие характеристики **не восстанавливаются** повторной генерацией.

Проверка наличия характеристик — простая, предсказуемая: известные **каталожные идентификаторы** (`Артикул`, `Код товара`, `SKU` и др.) не считаются техническими параметрами. Это не экспертная классификация всех возможных полей: нестандартные ключи требуют дополнительной настройки.

## Ограничения и возможные улучшения

1. **Исходные данные:** в предоставленном `feed.xml` отсутствуют развёрнутые описания и технические параметры для выбранных примеров. Выполнение целевого объёма 800–1200 символов при строгом запрете на выдумки иногда даёт общий, малоинформативный SEO-текст. Сервис не маскирует это как полную техническую карточку.
2. **Нет обогащения данных:** страницы сайта, веб-поиск и документация производителя намеренно не используются. Возможное развитие — отдельный подтверждаемый модуль импорта и обогащения, независимый от `POST /generate`.
3. **Эвристические проверки:** могут пропускать смысловые ошибки, повторы или необоснованные утверждения без числовых маркеров. Статус `generated` не гарантирует качество SEO и не заменяет контент-менеджера.
4. **Проверка вводимых данных:** значения считаются данными отправителя; программа не верифицирует паспорта и не знает о полноте всех возможных параметров конкретной модели.
5. **API-совместимость:** строгая схема ответа реализована через OpenAI-совместимый клиент и зависит от провайдера. Реальный API-вызов следует проверить с доступным ключом/локальной моделью.
6. **Прототип:** нет CMS, БД, очередей, деплоя и массовой обработки 47 тысяч позиций — это не требуется для локального MVP.

## Автоматические проверки

```powershell
python -m pytest -q
python -m ruff check .
python -m ruff format --check .
python -m pyright
```

Тесты не требуют LLM API и используют подставные ответы. Тестирование с реальным Codex CLI проводилось вручную для двух товаров. Изменение статуса `needs_review` после этих запусков покрыто отдельными тестами, но также требует повторной локальной проверки.
